Project

Tsunami

Network Automation for Windows · Open Source (GPL v3) · v0.7.2

A Windows desktop tool that replaces box-by-box CLI work with templated changes pushed to a fleet of Cisco IOS/IOS-XE and HPE Aruba AOS-S/AOS-CX switches, up to 200 per run, over SSH or serial console. Every change is shown as a diff against the live config before anything is sent. It has a GUI for people and a local MCP server for Claude. Claude can read inventory, draft plays, render templates and run read-only checks. It never sees credentials or secret values, and changes to customer devices need approval in the GUI.

Plays and runs

  • Plays from a GUI. Pick a play, pick targets, fill in prompts, preview the rendered config per device, then push.
  • Three play types on one engine: initial (day-0 staging over console or SSH, optionally adding the new device to the inventory), push (changes), and baseline (a per-customer standard config).
  • Four run modes: render (no connection), check (a diff against the running config, nothing sent), compliance (the lines a device is missing from its baseline, and the extra ones), and apply.
  • Layered variables across global, role, customer, site, device, play and prompt levels, with the source of every value shown. Prompts are typed and validated, with dropdowns for a site, role, hardware model or saved login.
  • Safe fleet pushes: apply runs a canary device first, then batches with a failure threshold, pre and post checks, a config backup, and rollback on failure or by a revert timer. The config is saved only when the checks pass.
  • Secrets as placeholders. Templates name a secret, or one field of it (an SNMPv3 user has several). Real values exist only in memory during apply, and a secret that a play uses but nobody saved is reported before anything runs.
  • History of every job, with masked renders and redacted diffs and output. Retry the failed devices, apply after a check, or run again. Show commands, discovery, drift checks and connection tests are recorded too.
  • Press and hold to reveal a masked value, after entering the Tsunami password again. Each reveal is audited.
  • SSH or serial console, including day-0 setup over the console, with a jump host per customer, site or device. Older switches that only offer SHA-1 SSH algorithms are reached through an automatic fallback.

Inventory and onboarding

  • An inventory tree of customers, sites and devices, with a default login per customer and per site, and logins on single devices.
  • CSV import, or editing through the inventory menus. Hardware models missing from the built-in catalog can be added per workspace.
  • Site discovery over CDP and LLDP: start from seed devices, add each one and follow its neighbors inside a scope. A separate check lists neighbors that are missing from the inventory.
  • Host keys trusted in bulk, without logging in. A changed key is shown with both fingerprints and replaced only after confirmation.
  • A page per device: the model, version and serial it reported, recent jobs, a connection test, its backups, and an SSH session in MobaXterm or OpenSSH.

Backups and drift

  • Backups from everyday work. Every apply, discovery, drift check and restore saves the config. The viewer shows one backup or compares two, always through the redactor.
  • Back up and check for drift on a site or a customer: a first backup for new devices, and for the rest a redacted diff since the newest backup.
  • Open in VS Code opens a redacted copy, or VS Code's diff of two. The raw file is never opened.
  • Restore from backup onto a replacement switch, over SSH or a console. The switch can be factory-new, in which case Tsunami answers its setup prompts. Rejected lines are listed, and the saved config is read back and compared with the backup. Restore is new in 0.7.0 and so far tested only against simulated devices.

Built for Windows

  • Runs natively on Windows 10 and 11. No WSL, Docker, Linux VM, database, or separately installed Python, and no agent on the switches.
  • Ships as a per-user installer that needs no admin rights. Builds are not code-signed yet, so SmartScreen asks once.
  • Device logins and secrets live only in Windows Credential Manager, encrypted under a Tsunami password. They never appear in YAML, git, logs, the job database, or MCP output.
  • The GUI is laid out like VS Code, with a command palette, quick open, tabbed views, and a Problems panel. VS Code stays the editor for the YAML and Jinja workspace, which is a plain git repo.

Claude, with guardrails

The MCP server's tools fall into three tiers. Tier 0 touches only the workspace: reading inventory, plays and job history, validating, rendering with secrets masked, and writing drafts. Tier 1 contacts devices read-only, for check-mode diffs, compliance reports, and allowlisted show commands on one device or many. Tier 2 requests changes. The policy sets the highest tier Claude may use, so a read-only setting stops every change request.

  • The relay holds no secrets. tsunami-mcp.exe relays each tool call over a local named pipe to the GUI, which runs it only while Tsunami is unlocked.
  • One redactor sits on every outbound string, verified by a dedicated secret-leak test suite. Every call is audited.
  • Claude writes only drafts. Drafts never reach a customer device until a person promotes them. The policy file lives outside the workspace and the server has no way to write it, so Claude can't edit its own permissions. It can read what it is allowed to do.
  • Show commands are allowlisted. Claude can ask for another show command, and a person approves it in Settings.
  • Inventory edits are off by default. When Settings allow them, Claude can add customers, sites, roles, devices and hardware models. Changing or removing a device is only proposed, and a person must trust a new device's host key before Claude can reach it.
  • Passwords stay with people. A password prompt is typed by a person for one run. Claude can't supply one, and no tool reads a backup or restores one.
  • Device output is untrusted. It comes back in a field named untrusted_device_output, and the approval gate covers prompt injection from banners or descriptions.

Approval flow

  1. Claude requests a run of an approved play, never a draft, against chosen targets.
  2. Tsunami renders every target and runs a check-mode diff. Devices that would change are marked ready. If none would, or if a device can't be checked, nobody is asked to approve.
  3. The GUI shows an approval card with the play, targets, prompts, and each device's masked render and diff.
  4. A person approves or denies. Approval records their Windows username and the time, and a request nobody answers expires.
  5. The job runs through the normal pipeline, with canary, backups, and rollback.
  6. Each device is re-rendered at run time. If the play or the render changed since approval, that device fails instead of pushing content nobody approved.

Until a person approves, the job reports that nothing has been applied. Inventory changes that Claude proposes wait for the same kind of approval, on a card that shows each field's value before and after.

Lab customers are the exception for runs: when the policy allows it, Claude can run plays against them without a click per run, so it can iterate against a CML lab. The job records that lab policy allowed it.

Architecture

Workspace

A folder of YAML and Jinja files: inventory (customers, sites, devices), plays, snippets, and a drafts area for Claude.

Engine

Validates, renders sandboxed templates with secret placeholders, diffs, and runs jobs with canary, batches, backups and rollback. It imports no GUI or MCP code, enforced by a test.

GUI

The only place changes are approved and run. It holds the unlocked credential vault and serves Claude's tool calls.

MCP server

A stdio relay for Claude Desktop or Claude Code. It holds no credentials and contacts no device itself.

Testing and CI

About 3,000 unit and 300 GUI tests. Every push to main runs GitHub Actions on Windows: lint, unit and GUI tests, and beside them a frozen build with self-tests, an MCP smoke test, and the installer. Integration tests run against a CML lab or a real COM port.

Stack: Python 3.12, PySide6, Netmiko, pyserial, Jinja2 (sandboxed), Pydantic v2, ruamel.yaml, keyring, cryptography, the MCP Python SDK, PyInstaller, and Inno Setup.
